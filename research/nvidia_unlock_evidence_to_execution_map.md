## 1. Target and definition of success

The objective is to safely implement and validate **a distinct GA102 and AD102 Windows preboot transaction** that can restore the currently restricted Tensor Core FP32-accumulation issue rate, hand off to the **unmodified** Windows NVIDIA driver, and demonstrate the actual performance and numerical result on each card. Tensor Cores already work; this is not a claim to add missing Tensor Cores or automatically double application throughput. NVIDIA CUDA P2P remains a **separate, excluded workstream** (`nvidia-smi topo -p2p` has shown `NS`).

The AMD iGPU has been verified as the independent passive preboot console in DIAG07–DIAG10; independence **during a vendor `Stop` transaction is not yet verified**.

A **successful per-GPU unlock** requires all of: exact target admission; safe one-device-only ownership transition; correct signed architecture-specific firmware source and execution; verified selector/permission readback; bounded DMA/PCI cleanup and FLR; stock Windows boot and device enumeration; matched pre/post HMMA rate plus numerical controls; and repeatable cold-boot/recovery observations. GA102 success cannot substitute for AD102 success or prove safe concurrent dual-GPU operation.

## 4. Required physical transaction and its stop/go checkpoints

This is the intended **future** sequence, **not an executed checklist**:

1. **Host preflight (no GPU mutation):** pin executable/asset hashes, driver/GOP image versions, both PCI/subsystem/parent identities, source licenses, current console and ownership graph, ROM authenticity and per-card cold-state eligibility. Reject unexpected revisions/unknown devices.
2. **Isolated NVIDIA GOP release (not enabled):** identify one exact target; preserve AMD GOP/console and the other NVIDIA device, record pre-call intent and watchdog-independent recovery strategy. `DisconnectController` reaches NVIDIA vendor `Stop`, whose destructor may read/write BAR0 `0x6104E0`/`0x610630` and poll without a local bound. `context+0x98==0` does not guarantee the destructor is read-only. Do not describe release as passive.
3. **Architecture-specific signed secure load (not enabled):** on GA102 use its verified GA102 FWSEC/SEC2/V67 path; on AD102 use separately verified AD102 signed Booter/4-PLM path. The Windows signed production asset source, descriptor and acceptance must be proven **before** any execution. CPU/GPU memory sources, lengths, bus mastering and DMA mapping lifetimes must be validated.
4. **Selector/permissions and cleanup (not enabled):** observe requested and effective tensor issue selectors and their permissions, avoid conflating GOP output mask `0x625E08+0x10*channel` or destructor registers with speed controls `0x82381C` / `0x823820`; drain DMA and verify PCI/BAR invariants before/after one target FLR.
5. **Stock boot handoff (not enabled):** return control to the unchanged Microsoft Windows Boot Manager only from a verified stage-complete state; collect precise post-handoff device/driver/health/selector evidence. No silent retry after partial failure.
6. **Proof and recovery (not enabled):** compare previously captured stock baseline to exact matched FP16/BF16/TF32→FP32 issue rate, FP16→FP16 control, numerical correctness and representative model inference; confirm clean cold-boot return separately. A vendor-side hang may not return for software rollback.

A failed identity, signature/provenance, device-ownership, DMA-lifetime or stage-status gate is a **STOP**, not a request to skip or weaken the check. Avoid attempting repeated active EFI boots after a partial transaction until physical state has been restored and examined. Passing a host simulator cannot establish hardware recoverability.
