## 1. Objective and decision

Develop a **one-card-at-a-time, preboot** process that can change the relevant NVIDIA Tensor Core FP32-accumulation issue-rate permissions, restore control to the **unmodified Windows NVIDIA driver 617.42**, and prove performance and numerical correctness on each GPU. The second target must remain installed and unchanged during the first target's operation. A same-boot **sequential** two-card process is a later, separate milestone. Parallel execution, CUDA peer-to-peer unlocking, permanent flash changes, unattended EFI persistence, and claims that Tensor Cores are currently disabled are not part of this goal.

**Current decision:** Passive identification and ordered two-card preparation **PASS**. Active NVIDIA release, signed firmware loading, selector writes, FLR, Windows-after-unlock proof, and cold recovery remain **BLOCKED**. Source and host tests are not permission to run a physical transaction.

**Terms:** UEFI means Unified Extensible Firmware Interface. GOP means Graphics Output Protocol. FWSEC is the protected firmware security stage. SEC2 is NVIDIA's security processor. DMA means direct memory access. FLR means PCIe Function Level Reset. ABI means the machine call contract. HMMA means the Tensor Core matrix-multiply instructions. See the investigation record for the original-driver function and firmware details.

**All four gates are false:**

`CAN_DETACH=false`  
`CAN_UNLOCK=false`  
`CAN_FLASH=false`  
`RECOVERY_VERIFIED=false`

No source, test, documentation or diagnostic result sets these to true. Any later active hardware test requires a separate reviewed procedure, recovery evidence, and explicit owner authorization.

### Stop-free ownership design gate — source specification, no executable route approved

**MSI B850 ordering, verified only where marked:** (1) The platform initializes PCI and may load/connect PCI option-ROM drivers; UEFI 2.10 allows platform and bus-specific Driver Override policy, but **the precise MSI 1A70 per-slot connect time, PCI option-ROM priority and DXE dispatch ordering are NOT captured**. (2) By the actual `GPU-TOPOLOGY-DIAGNOSTIC-0022.TXT` observation point, AMD `0000:0F:00.0` owns the only GOP and `ConOut/ErrOut`; NVIDIA AD102 `01:00.0` and GA102 `04:00.0` each already have original `BY_DRIVER=1` PCI ownership and zero GOP children. The two NVIDIA bind times relative to AMD GOP attachment and boot-manager `DriverOrder` are **unknown**. (3) The current `ReadyToBoot` DXE and launched UEFI app operate **after that observed NVIDIA binding** and call `GuMsiRelease()`; they cannot take ownership without vendor `Stop()`. (4) Windows' successful `ExitBootServices()` terminates the UEFI boot-service drivers, not necessarily their **device state**. (5) Windows PCI Plug and Play starts the parent bus before device-stack hardware-start stages, and WDDM eventually invokes `DxgkDdiStartDevice`; NVIDIA 617.42's precise callback registration/firmware activity timing and resource ownership remain **unproved**. **No measured MSI-specific total boot order exists. Do not invent one.**

**Path A: original MSI prebinding policy — SOURCE VERIFIED PORT ROUTES, CONDITIONAL SHARED MODE INHERITANCE, NO SAFE RELEASE.** Physical `0024` has 19 `ROM_CMN` modes, all 1. The 72/71 exact original `$PCIDATA` variants map the direct RTX 4090 route to `GPP0` first-child key 1 and the **AMD chipset bridge** `02:00.0` to `GPP7` first-child key 4, not the RTX 3080 itself. Original `FUN_00002AB8` limits *direct* inventory matching, but original `FUN_00003934` can share an ancestor's **existing option-ROM mode pointer** with deeper PCI devices when ROM BAR/entry conditions are met. Thus key 4 may indirectly influence the GA102, but not independently: it is an upstream bridge policy and can affect multiple chipset devices. This is not a verified safe per-card original NVIDIA `DriverBinding.Start` exclusion. The BIOS BDS legacy-policy route remains unavailable in the current selected UEFI mode. Do not write `ROM_CMN`, alter CSM/PEG or detach hardware. A safe owner transfer requires a source-proven selective first-bind gate or original NVIDIA cooperative no-Stop release plus separate recovery.

**Path B: NVIDIA-cooperative ownership (UNPROVEN / NO API).** Require an authenticated *stock* firmware/driver interface that explicitly permits external owner transfer and can acknowledge engine quiescence, memory/DMA disarm, PCI access release, and rollback/rebind **without invoking the zero-child destructor**. The observed private controller protocol and `context+0x98=0` do not grant such consent. Windows post-`ExitBootServices` device-specific lower filters are a *different* candidate boundary, but do not prove cold state, exclusive BAR access, stock vendor consent, safe driver start or signing; installation could restart both cards and is forbidden.

**Mandatory common acceptance before active work:** Pin original MSI board BIOS `E7E56AMSI.1A70`, original source code and loader hashes; verify on the same boot the exact ASUS AD102 `10DE:2684/1043:88E6`, ZOTAC GA102 `10DE:220A/19DA:B612`, separate PCI ancestor/bridge paths, one AMD `1002:13C0` console with independent `ConOut/ErrOut` and TextOut owner, no cross-target shared DMA/interrupt owners, and unchanged non-selected NVIDIA `BY_DRIVER` and hardware state. Linux assets and GSP ELF signatures do not qualify.

**Failure containment and recovery:** Before any mutation, ambiguous binding order, a live NVIDIA owner, missing signed proof, AMD/peer uncertainty or absent recovery evidence must **return unchanged** with no Stop, reset, flash, DMA or filter attach. After any future authorized state change, the first nonrecoverable/ambiguous status must latch a fault, stop any second-card action, prevent normal active handoff, and preserve evidence; software deadlines cannot interrupt an original vendor poll without a local timeout. ## 6. Failure rules and release conditions

- Before any mutation, a missing source, unknown ROM, unexpected peer, ambiguous console, invalid PCI path, absent recovery procedure or incomplete signed record **must fail without a driver Stop**.
- After any uncertain driver Stop, DMA, MMIO, SEC2, selector, FLR, S3 registration or EFI close result, retain the exact fault and ownership state. **Do not** retry, clear a sticky fault, switch to another GPU or continue normal Windows handover.
- Do not install or enable unattended DXE execution, alter NVRAM/BootOrder, modify Secure Boot trust, flash video BIOS, or patch the stock Windows driver to bypass an evidence gate.
- Use the original unmodified current Windows driver as the compatibility boundary. A Linux signed-reference asset is a comparison artifact, not a production acceptance record.
- For every future source change, verify the exact production function and independent failure cases through relevant existing host tests and Windows EFI builds. Record the command, result, source SHA and coverage in the commit/CI result, **not** as a dated report in this plan.
- For any future approved physical run, require before/after logs, exact binary and firmware hashes, explicit GPU identities, source evidence for each gate, recovery outcome and meaningful negative controls. An EFI success code, `UNLOCK_VERIFIED=UNKNOWN` or a benchmark speed alone does not qualify a release.
